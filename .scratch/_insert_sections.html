4. What's known, inferred, and undisclosed

Sources for this section: TypeSafe docs, Archer Hume's black-box probe ("Jev's Architecture Unmasked"), and TypeSafe's own jaggedness / FAQ pages. "Known" means TypeSafe or a public probe stated it; "inferred" is the strongest reading of those probes; "undisclosed" is still blank on purpose.

Known

  • Starts as a pretrained LM; post-training is RLCD (Reinforcement Learning for Calibrated Decisions) — TypeSafe's third branch after RLHF / RLVR (docs.typesafe.ai/introduction/machine-learning-primer).
  • One request = one state (up to 64k tokens; 32k for state plus the longest single question) + typed questions answered in parallel, in isolation.
  • Question types: Choice (≤255 options), Score, Noul. Output tokens are free; jev-1.13.0 is $0.042 per million input tokens (docs.typesafe.ai/models).
  • Typical hosted latency in our hands: 0.25–0.45 s per request over the network.
  • Probe: a secret planted in a sibling question gets 0.00 probability; the same secret in shared state gets 0.90–0.92.
  • Probe: state is encoded once — token accounting is strictly additive (one question 268 tokens, two 276).
  • Probe: latency is the same for 2 options or 255; output_tokens does not move with answer values — probabilities are read out directly.
  • Probe: adding an irrelevant option shifts odds between existing ones (list-wise scoring, not independent per-option logits).
  • Calibration on one public set: ECE 0.031 over 1,200 MMLU items.
  • Jaggedness (TypeSafe): reads instructions literally; cannot count or do date arithmetic; degrades with irrelevant state text; can be steered by adversarial content in state; English-first; not fine-tuned per customer.

Inferred

  • Backbone is almost certainly a causal transformer: 84.6% on MMLU-Pro needs frontier-scale pretraining, and RLCD is described as post-training.
  • Diogo Almeida co-invented RLHF — the family resemblance (LM + new post-training objective) is not an accident.

Undisclosed

  • Base model (tokenizer matched none of 192 public tokenizers), dense vs. MoE, exact loss, whether RLCD updates the whole network or just the head.
  • Launch FAQ leaves "training algorithm", "training data", and "public benchmarks" blank — not even a simple RAG retrieval comparison against chat LLMs or classical ML on a shared public set.

5. The open-source clones

Six open-source "clones" appeared within 48 hours of launch. All of them copy the interface (typed questions in, probabilities out) using the recipe Hume reverse-engineered: take an open LLM, pack state and options into one sequence, put a small head on the last position, train with plain cross-entropy on labelled answers.

Takeaways

  1. Clones were built for a different job. Their benches are short-text classification. Browser and phone agents need long state + many options in one pass (64k tokens, 255 options, parallel questions). No clone has published a number on that shape; the first time we tried, all failed on quality, not just speed.
  2. They are not calibrated — it shows when stopping. On the phone task kev and Nimble navigate, then never say "done". Jev stops at 0.77–0.81 confidence. Nimble's README: a 0.9 does not mean 90%.
  3. Hardware explains speed, not mistakes. M4/16 GB is 3–10× slower than authors' M5/32 GB or H100 machines (why kev-4b thrashed on 4k tokens). It does not explain wrong tickets, BLOCKED-before-looking, or never saying "done".
  4. What the $40M and secret data bought: general zero-shot behaviour, honest probabilities, and long context — from training data and objective, not from the architecture trick the community reproduced in two days.

Practical guidance

  • Fixed labels, short text, own labelled data: kev-0.5b/4b or Nimble locally is a real option — same answers as Jev, no API bill. Add post-hoc calibration before trusting probabilities.
  • Anything agentic (browser, phone, long documents, 20+ options): use Jev. Today nothing open gets close.
  • If you build on Jev: the model is rarely the bottleneck. Our browser loop spent 90% of time in the DOM reader and text helper; the phone loop spent 90% in the simulator controller.
  • The one test nobody has run yet: calibration on your data — bucket confidences on a few thousand of your own decisions and check whether the 0.8 bucket is right 80% of the time.

Three parties, one contract

Every publish target — hosted or BYOK — speaks the same POST /api/upload contract, authenticated by a bearer upload token. What differs is where that token comes from and who owns the Worker serving it.

FLOW 1 First-time onboarding · hosted default

Device flow auto-triggers on the first publish

Run /tdoc publish <slug> with no config (or pass --platform hosted). Because there is no valid hosted token, the CLI starts GitHub sign-in itself — you don't run a separate login command.

  1. No token in published.json CLI

    Missing config, or platform ≠ hosted, routes into first_time_setup_hosted. A stale platform:null is read as cloudflare — so pass --platform hosted to force the switch (old config saved as .bak.switch).

  2. Start device flow CLI → POST /api/auth/device/start

    Worker asks GitHub for a device+user code and returns user_code, device_code, verification_uri, interval.

  3. Authorize in the browser You

    CLI prints Code: XXXX-XXXX. You open github.com/login/device, signed in as the account you want to publish as, and approve. This one step decides the tenant.

  4. Poll until approved CLI → POST /api/auth/device/poll

    CLI polls every intervals (backing off on slow_down). On approval the Worker exchanges the grant, reads GitHub /user, mints session:<sid> in KV (30-day TTL, no GitHub token stored) and sets the cookie into the CLI's cookie jar.

  5. Mint the upload token CLI → POST /api/hosted/token session

    Gated by the session cookie. hostedAccountForGithub(login) looks up hosted-account:<login>, reuses the existing account_id or mints acct_…, then stores the token hashed as hosted-token:<sha256>. Returns {token, account_id, github_login}.

  6. Persist & upload CLI → POST /api/upload

    Config written 0600 with platform:hosted. Each version uploads with Authorization: Bearer <token>. First write claims the slug in the Durable Object; the doc goes live at tdoc.dev/d/<slug>.

Recoverable, not disposable. The upload token is a credential you can re-mint anytime by signing in again — account_id is derived from your GitHub login, so the same login always resolves to the same account and its docs.

FLOW 2 Multiple accounts · server-side tenancy

login → account_id → per-slug lock

The shared Worker keeps tenants apart with three layers. Nothing is scoped by the CLI or the machine — it's all keyed off the GitHub login proven at sign-in.

LayerKeyGuarantee
Identity hosted-account:<login> → account_id Same login always remints the same account_id (legacy hosted-github: keys reused). Stable & recoverable.
Credential hosted-token:<sha256> → {account_id} Tokens stored hashed, never cleartext. A bearer token resolves to exactly one account.
Ownership Durable Object, per slug First upload claims the slug. A second account gets slug_taken (409) / not_doc_owner (403) — it cannot overwrite, delete, wipe comments, or agent-reply.
Listing /me Shows only the signed-in login's docs. Per-account doc quota; re-publishing the same slug doesn't consume another slot.
One machine, one active tenant. published.json stores a single token. To publish as a different account from the same machine you re-run setup (or --platform hosted again) and authorize the other GitHub login in the browser — that overwrites the active token. There's no local multi-profile; the server keeps every account distinct, but the CLI holds one at a time.

The credential that decides the tenant depends on the platform

This is the easy-to-trip-on part: you may have gh CLI logged into several accounts, a wrangler login, and a browser session — and they govern different platforms.

FLOW 4 Hosted ⇄ BYOK · switching hosting

Same upload contract, different owner of the Worker

Platform is chosen on first publish and remembered. Re-passing --platform switches it: the CLI backs up the old config to published.json.bak.switch and runs that platform's setup from scratch.

Out-of-the-box

--platform hosted · default

  • Auth: GitHub device flow → session → account-scoped upload_token.
  • Infra: none to provision — tdoc's shared Worker + KV + R2 + DO.
  • Tenancy: enforced centrally by account_id + per-slug DO lock.
  • Serves at: tdoc.dev/d/<slug>.
  • Cost: free, always-on, zero infra.

Bring your own key

--platform cloudflare | vercel

  • Auth: wrangler / vercel login; a random TDOC_UPLOAD_TOKEN set as a Worker secret.
  • Infra: CLI creates R2 bucket + KV namespace (or Vercel Blob + Upstash KV) and deploys your Worker.
  • Tenancy: single-owner by construction — it's your account's Worker; owner_login from gh api user.
  • Serves at: your *.workers.dev / Vercel domain.
  • Cost: your cloud bill; full control & data residency.
Switch anytime — same slug, new home: /tdoc publish --platform cloudflare <slug> ··· the mismatch triggers full re-setup and rewrites published.json (old kept as .bak.switch). Hosting a hostname pair on one Worker (e.g. tdoc.dev + *.workers.dev) is not a switch.

FAQ Switching & multiple accounts · answered from review

What actually happens when you flip platform or account

Raised in review: does the backup get reused, what about switching back, multiple switches, and does the agent know which account it's on? Answers below, all grounded in bin/tdoc-publish.

  1. The .bak.switch file is a rollback copy, not a profile

    On switch, the old config is copied to published.json.bak.switch and only restored if setup fails (a trap on EXIT). On success it's kept but never read back, and every switch overwrites it — so only the immediately-previous config survives, not a history stack.

  2. Switching back re-runs setup — but lands you in the same place

    It does not reuse the backup file; it does a full re-setup. That's equivalent because state is recoverable server-side. Hosted: re-mints a fresh upload token, but account_id is derived from your login, so you return to the same docs. Cloudflare: re-setup is idempotent (R2 "already exists" is fine, KV looked up by title META) and just rotates the Worker's TDOC_UPLOAD_TOKEN.

  3. Multiple switches / multiple accounts are enforced server-side

    No matter how many times you flip locally, ownership is the account_id + per-slug Durable Object lock. Local config can't grant ownership you don't have — cross-account writes return slug_taken 409 / not_doc_owner 403.

  4. Switch platform vs switch account

    Platform: --platform <other> → backup + full re-setup. Account: there is no dedicated verb — re-run device sign-in (--platform hosted again, or delete published.json) and approve the other GitHub login in the browser; the token rebinds.

  5. Yes — the agent can tell which account is active, without a network call

    Source of truth is ~/.tdoc/published.json → github_login (+ account_id); the CLI also prints Signed in as <login> at sign-in, and tdoc-agent-reply --print-identity reports it. UX caveat: readable ≠ frictionless — switching account means re-running the device flow, there's no one-command profile select, and a machine holds one active tenant at a time.

  6. Two accounts: was publishing as #1, now want #2

    Re-run publish and approve account #2 at the device screen → new token bound to #2. Account #1's already-published docs stay owned by #1 — #2 can't overwrite them. To publish #1's docs again, re-authorize as #1.

DESIGN Keeping clients current · the too-old-to-nag gap

Client self-checks can't guarantee latest — the server has to

Today tdoc-update-nag runs on every publish: a git fetch origin main, compares HEAD vs origin/main, and nags on stderr if behind (Run: /tdoc update --yes). It never blocks and never auto-updates. It has one fundamental blind spot.

A too-old install can't warn you it's too old. The nag script itself shipped in a later version — an install predating it (this session's was 57 commits behind, with no nag file at all) literally cannot self-report. The notification only works once you're new enough to have the notification. It's also git-only (a non-git copy silently no-ops) and checks source parity, not compatibility with the deployed Worker.

Is a server-driven version signal standard? Yes — the norm is soft-nag by default, hard-fail only on breaking incompatibility.

DomainPrior art
Mobile appsFirebase in-app updates: min_supported from a config endpoint → force or flexible prompt.
HTTP APIsRFC 8594 Deprecation/Sunset headers; Stripe pins an API version per account; SDKs stamp User-Agent.
Protocol handshakesTLS, Postgres wire, Mongo wireVersion, Kafka ApiVersions — negotiate a range, reject only true incompatibility. The healthiest shape.
CLIsgh/stripe/wrangler print soft "new version" nags; terraform provider protocol & kubectl skew hard-fail on breaking gaps.

Why NOT force-update every time

especially for an out-of-the-box product

  • Breaks the "always works" promise — a blocking step at the exact moment the user wants to publish.
  • Update isn't atomic & can fail — diverged checkout, fast-forward blocked, network/permission — so an unrelated upgrade sinks the publish.
  • Availability coupling — one bad min_version push or a down endpoint can lock out every client at once; a typo becomes a global outage.
  • No pinning / reproducibility — CI & teams need a known-good version; force-latest can inject a regression they didn't opt into.
  • Churn & lost consent — surprise behavior changes; users lose control of when to absorb them. Offline users can't publish at all.

The shape to build instead

two-tier, fail-open

  • Server returns two numbers on /api/upload: min_supported (hard floor) and latest (soft).
  • Hard floor trips only when an old client would silently do the wrong thing — then return a clear, actionable message, not a raw error.
  • Everything else is a soft nag with a one-command update; never block.
  • Fail open — if the version check itself errors, allow the publish. Version infra must never take down the core action.
  • The floor moves rarely (security / unshippable incompatibility only); auto-update stays an opt-in convenience via the plugin marketplace.
Concretely for tdoc: the pre-multi-tenant CLI hitting the new sign_in_required and dumping a raw HTTP 401 is exactly the case a min_client_version on /api/upload should catch — turning a confusing error into "your tdoc is too old for hosted publish → /tdoc update". The client already calls the server on every publish, so it's zero extra round-trips.
